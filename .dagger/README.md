# relate-ci — merge gates as Dagger checks

The AGENTS.md "Final gates" as [Dagger](https://docs.dagger.io) checks. The same
definitions run on a laptop (`dagger check`) and on Dagger Cloud engines for every
push and pull request (Cloud Checks). This sits beside `.github/workflows/ci.yml`
and does not replace it.

| Check | Runs |
| --- | --- |
| `fmt` | `cargo fmt --all --check` |
| `clippy` | `cargo clippy --workspace --all-targets --exclude relate-python -- -D warnings` |
| `clippy-agent` / `-minimal` / `-serve` | `cargo clippy -p relate-cli --all-targets --no-default-features --features <bundle> -- -D warnings` |
| `boundaries` | `cargo xtask check-boundaries` |
| `test-cli` | `cargo nextest run -p relate-cli` |
| `test-cli-agent` / `-minimal` / `-serve` | `cargo nextest run -p relate-cli --no-default-features --features <bundle>` |
| `test-load` | `cargo nextest run -p relate-load` + `cargo test --doc -p relate-load` |
| `go-sdk/generate/stale` | the module's generated Go code is up to date |

The tests run under nextest, like the CI lanes, so each test gets its own process.
Plain `cargo test` threads can race on spawning freshly written scripts
(`ETXTBSY`).

## Usage

Needs the Dagger CLI 1.0 beta and a container runtime (Docker, Podman, …).

```sh
dagger check -l                      # list checks
dagger check                         # run them all
dagger check --check clippy          # run one
dagger check -j 2                    # at most 2 checks at a time
dagger check --engine cloud          # run on a Dagger Cloud engine instead of locally
dagger cloud checks list --watch     # follow the Cloud run for the current commit
dagger cloud checks rerun --failed   # re-run failed Cloud checks
```

Settings (constructor arguments):

| Setting | Default | Meaning |
| --- | --- | --- |
| `jobs` | `0` (one per CPU) | Caps `CARGO_BUILD_JOBS`. Lower it when the local engine is short on memory. A linker killed by signal 9 is an out-of-memory kill. Set it per user so the repo default stays uncapped: `dagger settings --global relate-ci jobs 4`. A `--global` setting is keyed by the workspace's git remote, so it applies to that remote only (a fork, or a `-W <git ref>` run of another remote, needs its own). |

## Caching

- **Results.** A check is a function of its inputs: the source (tracked files only,
  `.gitignore` applied) plus the toolchain image. Unchanged inputs replay the
  recorded result without running cargo. `.dagger/` is excluded from the source, so
  editing the pipeline does not invalidate every gate.
- **Build trees.** When the source does change, each gate reuses its own cargo
  target directory (cache volume `relate-target-<gate>`) and the shared registry
  volumes. Cargo then rebuilds only the crates the change affects.
- **Freshness.** Cargo compares mtimes, and source loaded from a git ref (as
  Cloud Checks loads it) has one fixed 1980 mtime, so a warm build tree would
  look newer than changed sources. Before cargo runs, each gate restamps the
  source from a ledger in its target volume. A file whose content hash is
  unchanged keeps its earlier stamp. A new or changed file (a revert included) is
  stamped now. The volume is mounted `LOCKED`, so two runs of one gate take
  turns.
- **Disk.** Each gate's build tree is several GB, and there are eleven of them.
  On a laptop engine, prune with `docker volume` / Docker Desktop's cleanup, or
  run on Cloud with `--engine cloud`.

## Files

- `dagger.toml`: the workspace. It installs the Go SDK and this module.
- `dagger.lock`: pinned SDK refs and images. Commit it whenever it changes.
- `.dagger/`: this module. `main.go` holds the checks; the `*.gen.go` and
  `internal/` files are generated by `dagger generate` and committed.
