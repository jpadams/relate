# Plugin system analysis — Relate extension mechanism (2026-09-25)

## Requirements (from Relate's constraints)

1. Embedded, single binary, no external runtime installs — rules out
   Python-in-process (embeds CPython per process, heavy) and native `.so`
   loading (unsafe ABI, kills the "one binary" promise on security alone).
2. Agent-first usage: extensions written by contributors and *generated by
   agents* — the sandbox must be strong enough to run untrusted code.
3. Two roles (see findings): row-source loaders/transformers and an agent code
   sandbox for analytics/memory/context.
4. Performance: hot path stays in Rust; extension calls are data-plane, not
   per-node inner loops.
5. Browser story: the planned WASM memory console wants the *same* engine and,
  ideally, the same extension mechanism.
6. Contract discipline: the openCypher TCK is the language floor — extensions
   must not fork the query language.

## Options

| Option | Safety | Speed | Contributor ergonomics | Single binary | Verdict |
|---|---|---|---|---|---|
| Native dylib (`.so`/`cdylib`) | none (full process access) | best | Rust ABI unstable, platform builds | no (per-platform artifacts) | **No** — this is the SQLite mistake |
| Lua via mlua (Luau sandbox) | medium (Luau-only sandbox; CVEs in the Lua sandbox history) | good | familiar language | yes (+~200 KB) | Fallback scripting flavor at most |
| Embedded JS (rquickjs/boa) | medium (engine bugs; platform support marked experimental on win-msvc/apple-aarch64) | good (300 µs startup) | best reach | mostly | Fallback for the browser build |
| Embedded Python (pyo3) | weak (no sandbox) | slow startup | best ecosystem | no (embeds CPython) | **No** for untrusted; keep our existing Python binding as the *client* story |
| Starlark | hermetic but no in-process preemption | ok | config-language familiarity | yes | **No** — runaway scripts can't be stopped cheaply |
| **WASM (wasmtime) guest modules** | strong (linear memory, deny-by-default host ABI, fuel+epoch+memory fences) | ~5 ms warm call, ~16 ms cold w/ AOT | any language compiles to it | yes (wasmtime crate) | **Yes — the mechanism** |
| Out-of-process (executable UDF / gRPC) | strong (process boundary) | per-block pipe overhead | any language, any runtime | no (external processes) | Later, as the Bolt-era answer |

## Recommendation

**WASM as the single extension mechanism, one capability-gated host ABI.**

- Host runtime: `wasmtime` with `consume_fuel` + epoch watchdog +
  `ResourceLimiter` (the denyx/sandboxd fence trio). Deny-by-default linker —
  no WASI initially; only audited host functions.
- Guest SDKs: start with Rust and JS/TS (via extism PDKs or our own thin SDK);
  Python guests can come later as wasm32-wasi components (py2wasm), keeping the
  host binary lean.
- Host functions (the capability surface — small and auditable):
  - `cypher_query(text, params) -> rows` — read-only by default; write requires
    a per-module capability flag
  - `emit_row(row)` — row-source plugins stream data into a query
  - `http_get(url)` — gated to a per-module host allowlist (the ClickHouse
    network-UDF pattern); this is how loaders reach SaaS/APIs
  - `kv_get/kv_put` — module-local scratch (agent-memory persistence hooks)
  - `log(msg)` — debugging, seeded random later if needed
- Call sites in Cypher: two surfaces only —
  `CALL plugin.rows('name', $args) YIELD …` (row sources) and a scalar
  `plugin.call('name', args)` for transforms. No new language constructs beyond
  a CALL pattern → zero TCK surface change.
- Distribution: single `.wasm` files + a manifest (name, version, requested
  capabilities, signature). A community registry can come later (DuckDB's
  `INSTALL x FROM community` model — but our signature check happens at load,
  and the sandbox, not the registry, is the security boundary).
- Trusted/fast path: performance-critical built-ins stay in-repo Rust behind
  feature flags (like our existing crates), never user-loadable.

### What we deliberately do NOT do (yet)

- No custom procedures/functions that extend the Cypher surface from
  extensions (Neo4j's APOC model). Extension roles are data-in and
  compute-over-rows only. If a need emerges, it's an ADR, not an accident.
- No language prototyping via plugins. Language evolution lives in the parser/
  planner in-repo where the TCK can gate it.
- No WASI sockets/files in v1 — loaders go through the allowlisted
  `http_get` capability, not raw syscalls.

### Fit with the roadmap

- The agent code sandbox *is* role 2: agents can `CALL plugin.run('analysis',
  $rows)` with fuel/time/memory limits — data analytics inside the database
  without trusting the code.
- The same wasmtime engine will power the browser console (the engine compiles
  to wasm; wasmtime-in-wasm via `wasm32-unknown-unknown` guests is possible,
  or fall back to rquickjs there — one exception, documented).
- Agent memory plugins (context graphs) become: `loader` reads chat history →
  `cypher_query` MERGEs entities → a later `CALL plugin.query('recall', …)`
  re-reads the graph. All within one `.rl` bundle.

## Cost/effort estimate

- wasmtime integration + host ABI: ~1 crate (`relate-ext`), 1–2 weeks to a
  working `CALL plugin.rows` demo.
- Manifest/signature/capability plumbing + docs + example loaders (CSV remote,
  GitHub API, agent-memory): another 2–3 weeks.
- Registry: later, only if contributors appear.
