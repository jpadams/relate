# ADR-0247: SF0.1 literals for the query-latency suite

> Renamed from ADR-0230: the number collided with
> docs/adr/0230-command-did-you-mean-on-parse-errors.md in #280 (both were
> taken by parallel PRs). The decision is unchanged; references were
> updated in the same change.

Status: Accepted

Date: 2026-10-14

## Context

ADR-0243 runs the 30 graph-benchmark-ldbc queries verbatim at both scale
factors. Upstream chose each query's literals (names, tags, places, IDs,
thresholds) on SF1, and most of them do not exist at SF0.1. Neo4j's SF0.1
answers (`expected-sf0.1.json`) are "nothing found" for 19 of the 30:
empty for q1-q7, q9 and q10, 0 for q13, q16 and q20, and `false` for q21
and q23-q27, q29. ADR-0243's Consequences record this: those queries still
search, but as answer checks they are weak, because an engine bug that
drops rows passes them. SF0.1 is the level that runs on every PR
(ADR-0243, ADR-0245), so the weakness sits exactly where the checks run
most.

Five of the 19 are "nothing found" at SF1 too, by upstream's design: q7
(empty) and q24, q25, q26, q29 (`false`). They check that a query finds
nothing when there is nothing, which catches false positives. The other
14 have rows, non-zero counts or `true` at SF1, and lose that only at
SF0.1.

## Decision

1. **SF0.1 runs upstream's query text with recorded literal
   substitutions** for the 14 queries whose SF0.1 answer is weak while
   their SF1 answer is not: q1-q6, q9, q10, q13, q16, q20, q21, q23, q27.
   SF1 stays verbatim.
2. **One table**, `workloads/gbl/literals-sf0.1.json`: per query, an
   ordered list of `[from, to]` pairs applied to the query file's
   statement as exact text replacements, and the reason for each choice.
   Every `from` must occur exactly once in the statement; a pair that
   matches zero or several times fails. The query files stay upstream's
   text, so the substitution is visible as a diff, not hidden in a copy.
3. **Only literals change.** A substitution replaces a string, integer or
   ID literal with another value of the same kind. Patterns, filters,
   aggregations, ordering and returned columns never change.
4. **How literals are chosen.** The SF0.1 answer must have the same shape
   as upstream's SF1 answer: non-empty where SF1 is non-empty, a non-zero
   count where SF1's is non-zero, `true` where SF1 is `true`. Within that:
   change as few literals as possible (keep the place, tag or person the
   query is about when it exists at SF0.1), replace a value with one of
   the same kind (a city with a city, a person tag with a person tag, a
   surname with a surname), and prefer a row count near SF1's. A query
   upstream checks as order-sensitive but writes without `ORDER BY` (q1,
   q3, q4, q5, q9) must answer at most one row: upstream's SF1 answers
   are one row, and with more the check would pin an order the query
   does not define (q4's first choice, two rows, came back from Neo4j and
   CypherLite in different orders).
5. **The five negatives stay verbatim.** q7, q24, q25, q26 and q29 answer
   "nothing" at both scale factors, so SF0.1 checks the same thing SF1
   does.
6. **Neo4j stays the oracle.** `expected-sf0.1.json` is regenerated by
   the examples repo's Neo4j lane (`./run.sh neo4j answers --sf 0.1
   --literals <table>`), which applies the same table; its `_source`
   records the table's sha256, and each answer the sha256 of the
   statement that ran. The suite's report records the sha256 of the
   statement it ran, so a report says which text was timed.

## Alternatives considered

- **Parameterise the queries** (`$name`) with per-scale-factor values —
  rejected: it changes upstream's text at SF1 too, and a parameter can
  plan differently from a literal, so the SF1 numbers would stop being
  comparable with upstream's and with the examples repo's.
- **A full copy of each query for SF0.1** (`queries-sf0.1/qNN.cypher`) —
  rejected: two copies drift, and the difference from upstream is only
  visible by diffing files. The table keeps one text and lists exactly
  what changes and why.
- **Make the five negatives positive at SF0.1 too** — rejected for now:
  SF0.1 would then check something SF1 does not, and the suite would lose
  its false-positive checks at the PR level. It can be revisited by a
  later ADR.
- **Check SF0.1 answers only at SF1** — rejected: SF1 is local-only
  (ADR-0243), so the per-PR level would keep 14 weak checks.
- **Choose literals with CypherLite's own answers** — rejected as the
  oracle: CypherLite was used only to explore the data for candidates;
  the recorded answers come from Neo4j (ADR-0243).

## Consequences

- 14 SF0.1 answer checks now have rows, counts or `true` to get right.
  SF0.1 latency for those queries measures the substituted text; no
  baseline has been frozen yet (ADR-0245), so nothing is re-frozen.
- The table is part of the workload: changing it means regenerating
  `expected-sf0.1.json` with the lane.
- The SF0.1 statements differ from upstream's, so SF0.1 numbers are not
  comparable with upstream's (which are SF1 only anyway). `NOTICE`
  records the modification.
- ADR-0243 and ADR-0246 get **Later references** notes naming this ADR.
