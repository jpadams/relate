# 0115. Sign release checksums with SSHSIG for offline install and upgrade verification

- **Status**: Accepted
- **Date**: 2026-09-27
- **Deciders**: CypherLite maintainers (Linear LABS-116)

## Context

The release pipeline (`.github/workflows/release.yml`, per ADR-0067) publishes
the raw CLI binaries `cypherlite-<os>-<arch>` together with a `SHA256SUMS`
manifest generated by `shasum -a 256`. Two consumers verify only that checksum:

- the in-binary `upgrade` command (`surfaces/cypherlite-cli/src/upgrade_cmd.rs`),
  whose design is fixed by ADR-0069;
- the `curl | bash` installer `install.sh`, whose asset contract is fixed by
  ADR-0068.

Both download the manifest **and** the binary from the same GitHub release.
A checksum proves the binary matches the manifest, but not that the manifest
is authentic: an actor who can alter the release can replace the binary and
regenerate `SHA256SUMS` in the same step. The signature and the thing it
protects arrive over the same channel, so the check cannot detect a tampered
release. This is the same-channel substitution gap tracked as **LABS-116 /
OPLANE_REQ-00262973**.

The fix must work for two very different verifiers:

- `install.sh` runs on end-user machines and must rely only on tools that are
  already present — it cannot ask the user to install a verifier.
- the Rust binary must verify a signature without a new heavy dependency
  (no native/C++ build, no async runtime, no networking).

Separately, `atomic_file::write_atomic`
(`surfaces/cypherlite-cli/src/atomic_file.rs`), which stages the downloaded
binary before renaming it over the running executable, currently syncs no
staged bytes and does not fsync the containing directory. A signature is only
as good as the file that ends up on disk, so the durability of that replacement
is folded into this decision.

Existing decisions referenced here: ADR-0067 (release policy), ADR-0068
(installer asset contract), ADR-0069 (lifecycle commands and self-upgrade
design), ADR-0113 (accepted TLS posture).

The decision below was settled by the maintainer before this ADR was written;
this record states it rather than reopening it.

## Decision

**Authenticate `SHA256SUMS` with an OpenSSH SSHSIG signature, verified offline
by both `install.sh` and the `upgrade` command, and make the atomic
replacement that consumes it durable.**

1. **Signature format.** Sign the `SHA256SUMS` manifest with `ssh-keygen -Y
   sign` and verify with `ssh-keygen -Y verify`, i.e. the OpenSSH SSHSIG
   format. The key is **Ed25519** and the signature namespace is
   **`cypherlite-release`**.
2. **One keypair, one secret.** There is exactly one release signing keypair.
   The private key is an unencrypted OpenSSH private key stored only as the
   GitHub Actions secret **`RELEASE_SIGNING_PRIVATE_KEY`**. The corresponding
   public key is pinned in the source, in **both** `upgrade_cmd.rs` and
   `install.sh`; verification never fetches the key from the release.
3. **CI signs the manifest.** In `release.yml`, after `SHA256SUMS` is generated,
   a step runs `ssh-keygen -Y sign -f <keyfile> -n cypherlite-release
   SHA256SUMS` and publishes the resulting **`SHA256SUMS.sig`** as a release
   asset. The key is written to a `umask 077` temporary file and removed on
   exit. The step fails when `RELEASE_SIGNING_PRIVATE_KEY` is unset, so a
   release cannot ship unsigned.
4. **`install.sh` verifies before checksumming.** The installer downloads
   `SHA256SUMS` and `SHA256SUMS.sig` and verifies the signature with the
   stock **`/usr/bin/ssh-keygen`** (`ssh-keygen -Y verify`), which is present
   on macOS and near-universal on desktop Linux, **before** the existing
   checksum step. No tool is installed and no network fetch of the key occurs.
5. **The Rust binary verifies before checksumming.** `upgrade_cmd.rs` verifies
   `SHA256SUMS` against its pinned public key using the RustCrypto
   **`ssh-key`** crate (0.6, features `alloc` + `ed25519`, MSRV 1.65) and only
   then checks the downloaded binary against the verified manifest.
6. **Fail closed.** If the `SHA256SUMS.sig` asset is missing, the signature is
   invalid or does not match the pinned key, or the verifier is unavailable,
   the install/upgrade aborts and the existing binary is left untouched. There
   is no "signature optional" or warning-only path.
7. **Durable atomic replacement.** `atomic_file::write_atomic` must `sync_all`
   the staged file before the rename, and on unix fsync the containing
   directory after a successful rename, so the verified bytes are durable
   before the operation reports success.
8. **Key custody and rotation.** Custody of the private key (protected Actions
   secret, no local copy) and the rotation procedure are documented in
   `RELEASING.md`.

## Alternatives considered

- **minisign.** A small, purpose-built signing tool with a simple format.
  Rejected: there is no stock POSIX-sh verifier, so `install.sh` would have to
  require the user to install a tool before the installer could check the
  release — exactly the friction the installer exists to avoid.
- **sigstore / cosign plus GitHub attestations.** Modern supply-chain
  attestation with transparency-log backing. Rejected: verifying in the Rust
  binary would add a heavy in-binary verification dependency, and `install.sh`
  would need `gh` or `cosign` on user machines, neither of which can be
  assumed present.
- **GPG detached signatures.** Ubiquitous in package ecosystems. Rejected: GPG
  key management and UX are heavy for this surface — keyrings, trust
  configuration, and interactive prompts do not fit a one-line `curl | bash`
  installer or a self-contained binary.
- **Keep the checksum-only status quo.** Rejected: a checksum and the artifact
  it describes come from the same GitHub release, so a release tamper replaces
  both and the check still passes — the same-channel substitution this ADR
  exists to close.

## Consequences

- A release can no longer pass verification after its `SHA256SUMS` is altered,
  unless the attacker also holds the release signing key: the public key is
  pinned in the clients, not fetched from the release.
- Both verifiers authenticate **before** they checksum the binary, so a tampered
  manifest is rejected before it can validate a substituted binary.
- `SHA256SUMS.sig` joins `cypherlite-<os>-<arch>` and `SHA256SUMS` as a
  load-bearing release asset; changing its name, format, namespace, or the
  pinned public key requires a new ADR referencing this one, ADR-0068, and
  ADR-0069.
- The private key becomes the single most sensitive release credential. Its
  compromise is equivalent to release compromise, and rotation moves every
  client's pinned public key, which requires a new release; `RELEASING.md`
  documents both.
- The `ssh-key` crate enters the CLI's dependency set; the engine crates are
  unaffected.
- `install.sh` depends on `ssh-keygen` being present. Where it is absent the
  installer fails closed rather than skipping verification.
